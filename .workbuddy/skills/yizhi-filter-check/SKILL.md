# 异兽志 · 筛选交互自检

## 何时用

- 动过筛选相关的任一处：`yizhi/js/main.js`（渲染筛选条 / 同步筛选条 / 应用筛选 / 渲染筛空）、`yizhi/js/views/grid.js`（通过筛选）、`yizhi/css/views.css`（`.chip` / `.chip-n` / `.zero`）、`yizhi/data/*.json`（吉凶值）。
- 要交「筛选三种情况测试通过」这类证据，而不是嘴上说通过。
- 提交前顺手跑一遍。

**不适用**：视觉版式（那是 `local-web-verify` 的活）。

## 它检查什么

四类规则的真源都写在项目里，本 Skill 只负责**验**，不负责定义：

| 类别 | 真源 | 断言什么 |
|---|---|---|
| 三态 | PRD §8.2 | 有结果=数量与站况对得上；无结果=出筛空面板且给出口；清空恢复=回到全量且按钮态复位 |
| 筛选条口径 | PRD §8.2 + TECH_DESIGN §9-6 | 每个值标条数；0 条只弱化（`dataset.空=1`）不禁用；多选读作「或」，站况里显式写「或」 |
| 无障碍 | `css/base.css` 的组件基线 | `aria-pressed` 跟选中态一致；chip 是原生 button 能 Tab 到；计数徽标是纯数字；焦点环在 |
| 契约边界 | TECH_DESIGN §6.2 | 只从 UI 外部驱动（点按钮），不 import 内部函数、不直接改页面状态 |

## 三个可观察的成功标准

1. **第一轮（原数据）的标记是 `PASS`**，明细共 16 条断言，覆盖：5 个 chip 及其计数徽标、有结果（点「吉祥」= 4 条 + 站况文案）、多选取「或」（选「吉祥 或 凶恶」= 6 条 + 站况显式写「或」）、清空恢复（点「全部」= 12 条 + `aria-pressed` 复位）、无障碍 4 条。
2. **第二轮（数据夹具）的标记也是 `PASS`**，明细里能看到「0 条值只弱化不禁用 → 点它出筛空面板 → 点出口回到 12 条」这 8 条断言全过。
3. **记录里 `数据夹具已还原` 为 `true`**，且跑完 `git status --short` 里不出现 `yizhi/data/yishou.json` —— 自检不留副作用。

## 为什么「无结果」要用夹具

异兽部 12 条的吉凶是 4 / 2 / 2 / 4，四值全覆盖；多选又是「或」，所以**光靠点击永远筛不出 0 条**，`渲染筛空` 这条 UI 路径在当前数据下不可达。

夹具做法：把 2 条 `"吉凶": "灾祸"` 临时替换成 `"无害"` → 「灾祸」计数变 0 → 那个 chip 进入弱化态 → 点它就走进了「基准非空却零条」的分支。

脚本用纯文本替换（不是重新序列化 JSON），跑完按原字节写回，替换次数必须是 2，否则直接报错停手。

- 别跳过还原那一步；别把探针页 `_probe-filter.html` 留在 `yizhi/` 里（属过程文件，也不该发布）。
- 别把第二轮（夹具）的断言当常态 —— 那一轮的数据是假的，只为走通分支。

## 已知边界

- 夹具替换依赖 `yishou.json` 里恰好有 2 条「灾祸」；数据改了要同步改脚本里的替换次数校验和探针里的期望表。
- 焦点环是**软断言**（无头环境下 `:focus-visible` 不保证匹配），记在 `软断言` 字段里，不参与 PASS/FAIL。本机实测匹配，结果是朱砂 `outline: solid 2px rgb(163, 48, 42)`。
- 只测异兽部（全站唯一有筛选条的一部）。
- **缓存是头号假故障来源**：Edge 会按启发式规则把 `main.js` / `css` 缓存进 profile，于是「改完代码重跑」跑的还是旧代码 —— 症状是「明明修好了，用例照样红」。脚本已两道堵死：服务端发 `Cache-Control: no-store`，每轮跑前清空 profile 目录。**新增用例时别把这两道去掉。**
- 数据文件一律用 bytes 读、bytes 写（本机 `core.autocrlf=true`，工作区是 CRLF；文本模式读写会做换行转换，还原后 `git` 会冒出一个「看起来改了」的假 diff）。
