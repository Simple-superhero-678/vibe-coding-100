# 异兽志 · 发布前检查（verify-project）

## 何时用

- **发布之前**：推 GitHub / 手动传 cbsite 之前，先跑一遍——坏东西别出门。
- **改过东西之后**：动过 `yizhi/data/*.json`（条数、id）、`yizhi/js/**`（语法、引用）、`yizhi/assets/**`（图）之后。
- **要交证据时**：需要「发布前检查通过 / 抓到了问题」这类可复现的证据，而不是嘴上说没问题。

**不适用**：视觉版式与交互正确性 —— 那是 `local-web-verify`、`yizhi-filter-check`、`tools/回归/` 的活，本 Skill 不重复它们。

## 它检查什么

十项、三组。每项都从本项目真实踩过的坑里来：

| 组 | 编号 | 检查什么 | 通过标准 | 来历 |
|---|---|---|---|---|
| 甲·安全红线 | A1 | 密钥扫描（调 `tools/scan-secrets.py`，自带阳性对照） | 对照 5/5 · 命中 0 条 | Day 23 两次凭据残留 |
| | A2 | 敏感路径忽略（`git check-ignore` × 5） | 5/5 命中 · `.env` 未被跟踪 | 私有原图 / 凭据红线 |
| | A3 | 站点目录卫生（`yizhi/` 扫描） | `_*` / `*.log` / `*.py` / `*.tmp` 0 个 | 探针页用完即删纪律 |
| 乙·线上活着 | B1 | Pages 站可访问 | HTTP 200（失败自动重试 3 次） | 发布目标必须活着 |

## 怎么跑

一条命令（本机 python 直跑，不常驻服务；跑完退出）：

```bash
C:/Users/lxb07/.workbuddy/binaries/python/versions/3.13.12/python.exe \
  "C:/Users/lxb07/WorkBuddy/vibe coding打卡学习/.workbuddy/skills/verify-project/scripts/run-check.py"
```

- `--标签 演示`：记录文件名加后缀（同一天跑多次不互相覆盖，如 `2026-10-13-发布前检查-演示.json`）。
- 退出码：`0` = 全绿；`1` = 有失败项；`2` = 脚本自身问题。
- 记录：`tools/自检记录/YYYY-MM-DD-发布前检查[标签].json`（含逐项状态、证据、发布全清单、git 附注）。

## 三个可观察的成功标准

1. **全项跑完是 `10/10 通过 —— 全绿，可以发布。`**，退出码 0；记录文件里十项逐条有「状态 + 证据」。
2. **故意弄脏会被抓**：`--演练`（见下）四步全符合预期：注入 → A1 红 → 恢复 → A1 绿。
3. **不留副作用**：跑完 `git status` 里不出现意外文件；`yizhi/js/station.js` 尾部没有 `<<<verify-project-演练>>>` 残留标记。

## 怎么证明它「不会虚报通过」

检查工具最大的风险不是漏查，是**永远全绿、看着安心、其实没查**。两条防线：

第一，A1 调用的 `scan-secrets.py` **自带阳性对照**（先拿假密钥验证正则能命中，再信「0 条」的结果）——Day 23 的思想。

第二，整条检查链路用 `--演练` 做阳性对照：

```bash
<python> .../run-check.py --演练
```

它做四步：往 `yizhi/js/station.js` **真注入**一行假密钥 → 跑 A1（**必须红**，不红就是虚报）→ 恢复原样（字节级校验）→ 复跑 A1（**必须绿**）。全符合预期才返回 0。假密钥由脚本运行时拼接生成，源码里不含能被扫描命中的完整串。

手工版（交作业演示用）：手动在任意站点 js 末尾加一行 `sk-` 开头的假密钥 → 跑全项（A1 应 FAIL 并列出文件与原文）→ 删掉 → 再跑（应全绿）。

## 千万别做

- **别为了让项变绿而动检查**：修根因；口径要变，先拍板再改（改完把口径写进这里）。
- **别跳过恢复**：`--演练`/手工演示后必须确认 `station.js` 干净（`git diff` 无输出、无演练标记）。
- 别把记录 json 当唯一证据——现场输出（stdout）才是第一现场，截图/日志从它来。

## 已知边界

- C1 的条数期望写死 30/20/13/20/14 —— **有意增删数据时**，要同步改脚本里的「五部期望」。
- C4 白名单按当前发布物类型（html/css/js/json/webp/gitkeep）——新增发布物类型（如 favicon.ico）时同步更新白名单；`.gitkeep` 这类点开头文件要用 endswith 判后缀（首跑冒烟曾误报，已修）。
- 乙组三项依赖外网（沙箱里走代理）——连续 3 次失败才判 FAIL，一次抖动不算。
- C3 只查静态引用（正则扫描）；动态拼接的 fetch 路径不在内，由「5 个数据文件存在性」兜底。
- 本 Skill 管「发布物对不对」，**不管**「页面好不好看、交互对不对」——那是别的 Skill。
