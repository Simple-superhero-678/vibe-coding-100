## 今日主题：故意弄坏哪一项？

我在**密钥扫描**这一项上做的手脚：往站点代码（`yizhi/js/station.js`）里真注入了一行假密钥——就是模拟「粗心把密钥留在代码里、还以为没事」的那种事故——然后跑检查。

结果两步都对：检查**变红了**，把文件和密钥原文都列了出来（截图里那行 `[FAIL] ... yizhi/js/station.js ← sk-demoFAKE…` 就是抓获现场）；把它恢复之后，复跑又变回绿的。

为什么挑密钥这项动手：

- 它是发布前最典型的「不可逆事故」——密钥一旦推上 GitHub，历史里就永久留底，删掉文件也没用；
- 它也是「发布前检查」存在的意义本身：拦住那些**推出去就收不回来**的东西。

这个方法有个名字叫**阳性对照**：先造一个「已知的坏」，验证检查确实抓得到；只有能抓住已知的坏，它的「全绿」才值得相信。这招不是今天发明的——Day 23 做密钥扫描时就先拿假密钥验证过正则，今天把它从「扫描器内部」升级成了「整条检查链路」。

## 卡点：检查工具自己也出了个 bug

最值得记的一条：冒烟第一跑，**检查器自己报了一个假警**。

`.gitkeep`（用来占位空目录的小文件）被判成「白名单外、会混进发布内容」。第一反应是去查项目——结果查下来是检查器的 bug：判断后缀那行代码用了 `os.path.splitext`，它会把 `.gitkeep` 这种「点开头」的文件名当成没有后缀，白名单自然对不上。改一行判断逻辑，复跑全绿。

这事好在流程里提前写了「**先生成、跑一遍、把误报漏报修掉、再跑第二遍确认**」。当时只觉得是个稳妥的习惯，今天它是真救了场——如果跳过「先跑一遍」，这个误报会一直潜伏：以后跑检查看到假红，就可能去改一个根本没问题的地方。

另外一个小坑：脚本里调的外部工具（git / node / curl）都做了「兜底路径」——因为这台电脑的 git 不在系统 PATH 里（是编辑器自带的便携版）。今天实测发现旧的兜底路径也失效过一个，最后按实测把三个工具的路径都校准了一遍。

## 感受与下一步

今天最大的收获不是会写检查脚本，而是想明白一件事：**检查工具最危险的状态不是「漏查」，是「虚报通过」**。

漏查，你知道它没查；虚报通过是它明明没工作、却一片绿油油——正则写坏了、判断写反了、环境不对了，输出照样「全绿，可以发布」。看多了这种绿色，人就会麻痹，把「全绿」当成「真的没问题」。所以给检查器本身装一道阳性对照，比多写五条检查项更值钱。

从今天起，「发布前检查」这一条命令就是每次推送前的固定动作。
