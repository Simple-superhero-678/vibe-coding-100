2026-10-02成长记录笔记

今天的题目是「接口返回的数据里，哪一项和你建的表对不上」。这题问得准，因为我写那份接口契约的时候，并没有真的跟表逐列对过。动手前先把三件事定了：课程里说的热搜、打卡示例跟我这个站对不上，我没出去找外部接口，把 /api/hot 改成对收藏表按条目聚合的收藏榜——真实数据不用外面拉，就是我自己库里的用户收藏；契约要求每个请求带 token，可库里没有存放 token 的地方，登录接口也还是占位，就先临时认地址栏里的 user_id，记成欠账明天还；前端今天不接，只交接口本身。

对账下来，契约里有五项在表里找不到落点。最扎眼的是认证：契约写着每个请求都要带 Bearer token，可全库没有任何 token 或会话的落点，等于「要求验身份，但系统还没有身份这回事」。剩下四项小一些。响应里的 total 在 favorites 里没有这一列，只能另外跑一次 count。参数 bu 想按部过滤，可表里根本没有「部」这一列，部归属只活在前端那些 json 里。排序写的 created_at 不是唯一键，同一秒批量写进去会撞在一起，分页会重复或者漏行，实现里补了 id 兜底。还有时间，驱动把 timestamptz 转成 Date 之后序列化会多出 .000，跟契约示例对不上，最后在 SQL 里直接格式化成字符串绕过去。

接口落在 cloudbase/functions 下的 favorites 和 hot 两个目录，本机拿假查询器跑断言，从 31 条加到 44 条全过。部署这一段超出预期：我以为又要回控制台点十几下，结果发现本机早前登录过云开发的命令行工具，里面还打包了一个本地 MCP，建函数、配环境变量、挂路由、查库我都能直接调，一天下来一次控制台都没点。真库里 favorites 九行、users 五行，接口读出来 total 是五；我改掉一条 entry_id 再刷新，返回的第一条立刻跟着变，改回来也立刻复原。

只有数据通路是被逼着换的。控制台的「连接信息」入口在这个环境根本不存在，拿不到数据库连接串，官方的 pg 直连又被列成要配 VPC 和白名单的例外路径。改成走官方的 PG HTTP 网关加环境密钥，响应形状一个字没变。那是 PostgREST 形态，不支持 GROUP BY 和 count 聚合，榜单只能把条目拉回来在函数里自己算；它返回的时间带 +08:00 偏移，也在函数里统一转成契约要的 Z 结尾。

拉胯的地方有两处。一是那份契约是我自己写的，今天逐项对账才发现 total、部、token 三项当时就没跟表对齐，等于拿一份没核实过的依据往下走，「接口要什么」和「表有什么」这两件事得同时写、同时核。二是推送，我默认沙箱推不上去，前几天还劝自己手动来，今天抱着试一次的心态跑了一条命令，一次就过。把没验证过的结论当默认，跟今天这个题目其实是同一个毛病。明天把登录接口补上，把临时认的 user_id 换成真的 token。
