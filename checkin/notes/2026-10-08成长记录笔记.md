## 今日最值钱的发现：跨域问题是怎么被认出来的

**起点是一个疑问**：清单说「配置跨域，禁止 `*`」，但我记得 Day 17 时代码里已经写了 `access-control-allow-origin: '*'`——那今天到底要改什么？

**第一步：不信记忆，抓真实响应头。** 用脚本带上 `Origin` 头打线上接口，把响应头整个抄下来。 favorites 的响应里出现了这个：

```
access-control-allow-origin: https://…tcloudbaseapp.com,*
```

**两个值拼在一起了。** 而 CORS 规范里这个头只能有一个值——浏览器见到双值会直接拒收。也就是说：如果当时直接把前端接上去，所有请求都会被浏览器拦掉，而且报错信息极难读懂。

**第二步：对照实验定位来源。** 同样的请求打 health 接口（它从来没写过 CORS 头），响应头反而是干净的单值。这一对照就清楚了：`https://…tcloudbaseapp.com` 是 **CloudBase 网关反射**出来的，`*` 是 Day 17 我们自己写在函数里的——**两套 CORS 机制在打架**，而且打架的结果是非法头。

**第三步：用不同 Origin 探网关的规则。** 换三种身份打探针：

| 我假装来自 | 网关反应 |
|---|---|
| 自己的静态托管域名 | 反射放行（单值干净） |
| `localhost:8000` | 也反射放行（本地调试不用额外配置） |
| `https://evil.com` | **不反射**——陌生来源直接不给 CORS 头 |

结论：**网关本身就有白名单语义**。所以正确修法不是在函数里写更聪明的头（写了必然和网关拼接成非法双值），而是**把函数里的 `*` 整个删掉**，白名单交给网关。禁通配符的要求天然满足：代码里不再有 `*` 字面量，陌生域名实测拿不到放行头。

**一句话总结**：跨域报错难查，是因为它发生在浏览器和网络之间，代码里看不到。破解办法就是「抓头 → 对照 → 变量分离」三步——先拿到真实响应头，再找一个没这个问题的地方做对照，最后每次只变一个变量去探对面的规则。

## 卡点

1. **health 接口的返回没有 `data` 包装**（`{ok:true,service}`，Day 15 早期形状），前端按新契约拆 `data` 拆出 `undefined`，报 `Cannot read properties of undefined`。修法：有 `data` 拆 `data`，没有就整体给。——教训：**同一条契约链路上的接口，形状可能因年代不同而分叉**，薄层要做兼容。
2. **「读取中…」占位残留**：格子落终态时只 append 不替换，文本永远含「读取中」，自动化探针判定全假。修法：终态整格重建。——教训：**占位符是有生命周期的，落终态时必须收走**。
3. **单线程 HTTP 测试服务器被 hang 请求堵死**：为了让 Edge 延迟截图而挂起的一个请求，把整个测试服务器排队堵死，页面资源全加载不出。修法：换 Threading 服务器。——教训：**测「慢」的资源时，别让等待本身堵死别人**。
4. push 第一次挂住（代理 401 要账号形态），重试脚本第二次 11 秒过——「凭据其实是好的，原样重试」又一次应验。
